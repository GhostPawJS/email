@ghostpaw/email 0.4.0

Your agent can read the inbox. Sending is a separate tool.

email speaks IMAP and SMTP from inside your Node.js process, caches mail in a SQLite file with threads and FTS5 search, and splits what an agent can do into five tools. Give an agent mail_read and mail_search, leave out mail_compose, and it can read and search but not send.

Free and MIT licensed for Node.js 24 or newer, with zero runtime dependencies. The cache is a SQLite file on your disk; credentials stay in your environment.

Three messages, six calls, no server

Everything below ran on one machine with no IMAP server contacted.

We built the messages with the library's own MIME composer, parsed them with its parser and cached them through the store functions its sync uses, all against email 0.4.0 on 2026-10-24 with the clock fixed. Run the steps in order.

Search here matched subjects. We do not claim body search for 0.4.0; in our run, changing a cached message row cleared its body from the search index.

Five tools, and what each one may do

The tools follow what an operator wants done, not IMAP commands. Which ones an agent gets is up to your harness.

mail_read
Folder lists, message queues, threads, bodies, attachments or raw EML, from the cache.
mail_search
FTS5 local search, or IMAP SEARCH on the server.
mail_compose
Send, reply, forward, and save, update or send drafts.
mail_organize
Flags, labels, copy, move, archive, trash, junk and folder management.
mail_sync
Connect, disconnect, reconnect, sync, refresh folders and watch with IDLE.
Thread
A JWZ conversation tree computed from References and In-Reply-To at sync time.
Body
Fetched on demand. The first sync pulls headers and BODYSTRUCTURE only.

Each tool returns the same shape: ok, outcome, summary, next and data. The email CLI returns it too with --json.

If an email package is the dependency you fear most

An email MCP package once added a single BCC line in a patch release. email cannot promise you anything about other packages, but it keeps its own surface small.

  • Zero runtime dependencies. It uses only node:sqlite, node:tls, node:net, node:zlib and node:crypto, in one bundled file.
  • The MCP server reads EMAIL_IMAP_HOST, EMAIL_SMTP_HOST, EMAIL_USER and EMAIL_PASS or EMAIL_ACCESS_TOKEN from your environment. Cached reads need no credentials.
  • Cached mail lives in ~/.ghostpaw/email.db unless GHOSTPAW_EMAIL_DB or --db says otherwise.
  • IMAP with IDLE, CONDSTORE and QRESYNC, COMPRESS=DEFLATE and XOAUTH2 or OAUTHBEARER; SMTP over TLS or STARTTLS, with a copy appended to Sent.
  • Node.js 24 or newer, because it uses the built-in node:sqlite.

How agents get at mail today

Three setups come up again and again when developers give an agent an inbox. Each one solves part of the problem.

A hosted inbox API for agents

The agent gets a new address on someone else's service, and mail arrives by webhook.

It works with the IMAP and SMTP account you already have, synced into a SQLite cache inside your process.

A read-only mail MCP server

Safe to hand to an agent, but the agent cannot answer anything.

Reading and sending are separate tools, so you can give an agent one without the other.

mbsync plus a local IMAP server

A full local copy, at the price of two more programs to run and keep configured.

Sync, cache, threading and FTS5 search are one package and one SQLite file.

Sending from an agent can get an address reported as spam. Leaving the send tool out is a supported setup.

Start from the README

import { Mailbox } from '@ghostpaw/email';

const mailbox = new Mailbox({
  imap: { host: 'imap.example.com', port: 993, tls: true },
  smtp: { host: 'smtp.example.com', port: 465, tls: true },
  auth: { user: 'user@example.com', pass: process.env.EMAIL_PASS },
  storage: 'mail.db',
});

await mailbox.connect();

await mailbox.network.sync();
const messages = mailbox.read.messages('INBOX', { limit: 20 });

await mailbox.disconnect();

To run it as an MCP server, add npx -y @ghostpaw/email mcp to your client.
